# TASK-090 — Evidence collection runs: scheduler, BI call, request, form, manual

Owner decision 2026-10-20 (DEC-031). TASK-089 gave every evidence item a collection method, its settings and a schedule, and a pure `nextOccurrences(schedule, from, count, terms)`; nothing runs from them yet. This task makes them run.

To build:
- **A scheduler job** (pg-boss, in the worker; one import point, DEC-024) that finds the items whose `next_due_at` or next occurrence has come, makes **a run for the period** (idempotent: one run per item and period, whatever the job's retries), and moves `last_run_at` and `next_due_at` on. The semester schedule reads the academic calendar; a period the calendar does not define makes no run and stays flagged (`scheduleGap`). Recompute `next_due_at` when the calendar changes.
- **A run** (`evidence_run`): the item, the period (start, end, label), the due time, a status `pending | requested | supplied | late | failed | skipped`, who or what supplied it (the new evidence version), and the reason for `failed` and `skipped`. `late` is set by the job when the due time passes without a supply; a late run still takes a supply. Same-institution checks, RLS, audit, and the worker's role may write runs but never approve or publish anything (DEC-006).
- **By method**:
  - `bi`: send the BI API request (the endpoint resolved from the server's environment by `endpointKey`, never a typed address; the structured query and period grain from the item; the timeout) and wait for the response; a refusal, an error or a timeout makes the run `failed` with the reason, to be retried or skipped by a person. A **per-run one-time token** for the BI's callback (stored as a hash, expiring, used once) lets the BI supply asynchronously: the supply becomes a new evidence version with `as_of` and lineage, and the run `supplied`. See docs/ams-bi-contract-v0.md 3.6 and 4.
  - `request`: send the evidence request to the person or the email address (the existing evidence request service and one-time link, DEC-018), with the item's note; the run is `requested` until it is answered.
  - `form`: open the dataset's online form for the period (the existing form, DEC-020); responses join the data when a person adds them, which supplies the run.
  - `manual`: create the owner's task (it appears in My work) with the item's instructions and expected format; a new version added by the owner supplies the run.
  - `survey`: reserved; makes no run.
- **Screens**: the evidence card lists its runs (status, period, due, what supplied it) with Skip this period (a reason) and a manual "Run now" for a person who may write evidence; a Late flag; the owner's task in My work.
- **Notifications** (in-app, with the notification work of TASK-088): a run is due, requested, late or failed.
- Tests: scheduler idempotency and the period boundaries across daylight saving, one per method (the BI call against a stub endpoint, its failure, its timeout, the callback token used once and expired), late, skip, the calendar gap; database rules; API; web; responsive states.

Open for the owner: whether a failed BI run retries by itself (and how often) or waits for a person; whether a late run keeps asking; how the dataset's `source_kind`/`source_config` (governed metric, PRD 9.4) and the `bi` method are reconciled (the proposal: the method says WHEN and by WHOM it is collected, the source configuration says WHAT the governed metric is).

Built (2026-10-21), decisions in DEC-032, migration 0065_collection_runs.sql (journal idx 65, `when` 1792050000000, forward-only):
- **The run** (`evidence_collection_run`): item, period (`period_label`, `scheduled_for` = the day the schedule placed it, `period_end`), `due_at`, `status` (pending | requested | supplied | late | failed | skipped), `trigger` (schedule | manual), the supplying `version_id`, `requested_at`, `responded_at`, `attempts`, `last_error`, `next_attempt_at`, `details`, the BI's `callback_token_hash` and `callback_expires_at`, `skip_reason`. One run per item and period (unique key). Tenant RLS (a restricted item's runs are seen with the item), stamp and audit triggers, a status guard (supplied and skipped are final; failed -> requested is the retry; late -> supplied is allowed), same-institution checks (the item, and the version must be the run's own item's), checks that a supplied run has a version, a skipped one a reason, a failed one an error, and a trigger that clears the one-time token the moment a run is supplied, skipped or failed (single use). The app skips, retries and supplies; nobody deletes a run. `evidence_request.collection_run_id` ties a request to its run.
- **The worker's narrow grants** (each backed by a trigger or a policy, db test `collection-runs.test.ts`): insert and update runs in the columns a run needs (it cannot skip one, change what it is about, or delete); `UPDATE (next_due_at, last_run_at)` on the item; insert an evidence version only when its lineage names the BI; insert an evidence request only when it has a run; `UPDATE (form_open)` on a dataset's spec only to true; insert notifications of the three `collection_*` kinds only (the old TASK-088 test that said the worker never writes notifications now says "only these"). `collection_institutions()` is the one narrow question the tick asks (SECURITY DEFINER, worker only); `app_resolve_collection_callback(run)` finds a run's token hash and expiry for the callback (app role only).
- **The scheduler** `collect_tick` (new job type in `JOB_TYPES`, group `worker` in `QUEUE_GROUPS`, `WORKER_QUEUES` in compose.yaml; a pg-boss schedule every 15 minutes declared by the general worker service; no job row): `packages/core/src/collection/tick.ts`. Per institution under a system identity with the worker role: make the due runs (first time only the current period, later every period begun since the last, never before the start date, a semester the calendar lacks makes none; `last_run_at` and `next_due_at` kept, which also recomputes a semester item's next due when the calendar changed), carry out each new or retryable run (the BI call is made between two transactions), mark late the runs past due (once; the owner is told once). A failure of one run is kept on it and never stops the tick. Idempotent: safe to run twice.
- **By method** (`collection/execute.ts`): `bi` calls the BI through the one `BiClient` (`bi-client.ts`: `POST {BI_BASE_URL}/ams/collect`, bearer `BI_API_KEY`, https only, `endpointKey` resolved by `BI_ENDPOINTS`, timeout from the item or 60 s) with the documented body and a per-run token; 200 = the supply (checked and stored as a version with origin bi, `asOf` and the BI's lineage under `lineage.bi`), 202 = wait for the callback, anything else = failed with the reason and attempts + 1, retried after 15 min, 1 h, 4 h, 12 h, five attempts, then the owner is told; settings errors are not retried; `request` sends an evidence request for the run (a file request for a document, a form request for a dataset) and its answer is a new version of the item itself; `form` opens the dataset's form and adding responses to the data supplies the run; `manual` tells the owner (in-app notice and My work). A new version of an item by a person (file, address, saved rows, responses added to the data) supplies its oldest open run (`collection/hook.ts`).
- **The callback** `POST /api/bi/v0/runs/{id}/supply`: authenticated only by the run's one-time token (`Authorization: Bearer`, a new `runCallback()` access kind of the route chain, listed with the link routes in `pnpm test:routes`), hash compared in constant time, expiring (14 days), used once; 401 for every token failure, 409 when the run is not waiting, 422 with the issues for a body that does not fit the item (rows against the columns, a file over the size limit, a document sent rows) leaving the token valid. `GET /api/bi/v0/runs?updatedSince=` is NOT built (contract section 5 stays planned).
- **People**: `GET /api/collection-config` (is the BI set up; no secrets), `GET /api/collection-runs` (status, item, owner, mine, due filters), `GET /api/evidence/{id}/runs`, `POST /api/evidence/{id}/runs/now`, `POST /api/collection-runs/{id}/skip | retry | supply` (evidence:read / evidence:write; Run now and Retry carry the run out in the request). The evidence list carries `runCounts` (open, late, failed) and a notification carries its `run`.
- **Screens**: the Collection section of the evidence card lists the runs (period, due day, status chip, "Supplied by version N", the error, attempts and next attempt of a failed one, the skip reason) with Run now, Retry, Skip this period (a required reason) and Mark supplied (choose one of the item's versions), and says "The BI is not configured" for a BI item while the server has no BI; the library has Due soon, Late and Failed filters and Late / Failed chips; My work has "Evidence to supply" (Supply <evidence> for <period>, Late chip, Open -> `/evidence?item=`) and Open on collection notices; the My work count includes the runs. New chrome through `t()` (`coll.*` keys; `components/collection-runs.tsx` is in CONVERTED_UI); Arabic names `dir="auto"`; no side panels; responsive states added to e2e/responsive.mjs (the runs in every status, the Skip dialog, the Late filter, the Arabic page).
- **Config** (all optional): `BI_BASE_URL`, `BI_API_KEY`, `BI_ENDPOINTS`, `APP_PUBLIC_URL` (default `APP_URL`), documented in `.env.example` and compose.yaml. With `BI_BASE_URL` empty a BI run fails with "The BI is not configured: set BI_BASE_URL ..." and nothing crashes.
- Tests (full run 2,045 tests in 190 files, database, route-permission and migration tests included): core `collection/collection.test.ts` (27: runs per period for day, week, month, quarter, semester, year, the semester gap, no duplicates on a repeat tick, daylight saving in New York; manual, late, form, request for a document, an address, a dataset and a skip; bi sync, file and address, 202 then callback, token wrong / other run's / used / expired, a body that does not fit, five attempts with the backoff, not configured, endpoint and https rules; the HTTP client; Run now, skip, retry, supply, listing), database `collection-runs.test.ts` (23), API `collection.test.ts` (10: permissions, the callback with every token failure, 422, 409), web `collection-ui.test.tsx` (11), the worker `queues.test.ts` (the schedule and the compose file) and updated db `evidence-schema.test.ts` and `notifications.test.ts`; responsive states in e2e/responsive.mjs.

Decisions taken here (not in the brief, recorded in DEC-032 or here): the retry delays (15 min, 1 h, 4 h, 12 h) and five attempts; a late run does not keep asking; the first tick of a schedule makes only the current period (no backfill of years); the BI's own lineage is nested under `lineage.bi`; a body over the size limit is 422 with `issues[0].path = fileBase64`; the callback token lives 14 days; a `request` item that is a dataset is asked for through its form (the answer waits until someone adds it to the data), a document through a file; a request to an address without an account waits, since email is not sent yet (TASK-061), and the owner is told to copy its link from the Requests tab; the scheduler does not see restricted items (system identity), so it does not collect them; a version added by a person supplies the oldest open run whatever the method; a `late` run can still be supplied (or skipped) but not retried; the notice kinds are collection_due, collection_late, collection_failed.

Not done: `GET /api/bi/v0/runs?updatedSince=` (the AMS asks the BI itself); email for requests (TASK-061); a catch-up cap after a long worker downtime (it makes one run per missed period, up to 500 per item and tick); the dataset's `source_kind` / `source_config` are not read by the runs (the method says when and by whom, the configuration says what; reconcile in M9); the PRD §6 table is not edited (DEC-031 and DEC-032 win); the Settings page has no BI section (the not-configured state is on the item's Collection section).
