title: >-
  The AMS is the BI's authorization server: OAuth 2.1 with PKCE and OpenID Connect, tokens verified by the BI with
  published keys, carrying a BI role and data scope derived from AMS role assignments
status: accepted
context: >-
  The BI asked (drmoyassine/ai-native-bi#10, AMS issue 3, 2026-10-27) for a person identity: its app, MCP clients such
  as Claude and later BI tools must act as a person with that person's rights, and when the BI runs with the AMS those
  rights should come from the AMS so there is one account, revoked in one place. Contract section 6 defined only the BI
  as a service. The owner asked for the decision, the contract section and the build.
decision: >-
  The AMS issues tokens for the BI with Better Auth's oauth-provider and jwt plugins: issuer APP_URL/api/auth, discovery
  under the issuer and at the root (RFC 8414), EdDSA keys published as JWKS, authorization code with PKCE required for
  every client, refresh tokens rotated. Clients exist only in the server setting OAUTH_CLIENTS (confidential with a
  secret, or public); no dynamic registration, no consent screen. Access tokens have audience BI_OAUTH_AUDIENCE and last
  10 minutes, ID tokens 1 hour, refresh tokens 30 days. Every token carries ams_user_id, ams_institution_id, email,
  name, bi_role (viewer, steward, admin) and bi_scope (institution, org unit and program ids with a role on each), read
  fresh at every token and refresh from the AMS role assignments: institution admin is admin; a narrower admin or a lead
  is steward; the other reading roles are viewer; an external reviewer gets nothing; an engagement role counts on the
  engagement's subject. A person unknown, inactive or without such a role gets no token (403 access_denied), so
  disabling a person stops the BI at the next refresh. Institution single sign-on is federated through the AMS.
rationale: >-
  Standard OAuth and OIDC let the BI and any MCP client verify tokens themselves with no shared secret and no access to
  the AMS data. Deriving the BI role from existing assignments needs no new screens and keeps one source of truth for
  who may see what; reading it at every refresh with 10-minute access tokens makes revocation effective without a push
  channel. Listing clients in configuration avoids open registration and a consent screen, and an MCP client such as
  Claude accepts a pre-registered client id.
consequences: >-
  New: migration 0069 (the plugin tables outside RLS, and app_bi_principal, a SECURITY DEFINER read of a person's
  assignments), packages/core bi-identity (the role mapping), the issuer in apps/api auth.ts with seedOAuthClients at
  start-up, root discovery routes, the sign-in page continuing a client's request. Contract section 6.2. Planned:
  dynamic registration with a consent screen, an explicit BI role, an audit event per sign-in, and the org chart read
  (open question 6) so the BI can resolve scope ids.
