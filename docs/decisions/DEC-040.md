---
title: 'API keys let other systems call the API: an admin issues a named key with one role; it acts as its own service user'
status: accepted
context: >-
  The owner (2026-11-16) wants programs, PEOs, PLOs and the rest to have API create, read, update and delete. The API
  had those routes, but only a browser session (or a one-time BI callback token) could call it, so no other system
  could.
decision: >-
  An administrator issues API keys in Settings -> API keys, each with a name, one role across the institution (admin,
  lead, contributor, reviewer or viewer) and an optional expiry. A key is `ams_<id>_<secret>`, sent as `Authorization:
  Bearer`; it is shown once, only its SHA-256 is stored and it is compared in constant time. Each key acts as a service
  user of its own (an app_user "API key: <name>" with that role), so permissions, row-level security and the audit trail
  apply to it unchanged. A key is revoked (never deleted), which also deactivates its user; a wrong, revoked or expired
  key answers 401 with no fallback to a session. Its last use is recorded at most once an hour.
rationale: >-
  A service user per key reuses the whole permission and audit model instead of adding a second one, and makes every
  call traceable to the key that made it.
consequences: >-
  Managing keys needs institution:write (administrators). Keys hold institution-wide roles only; scoping a key to a unit
  or program, and rate limits, are later work.
