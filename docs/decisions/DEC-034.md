title: >-
  The AMS and the BI may be deployed together in one Compose project, sharing the database server and the object store,
  each with its own database and bucket
status: accepted
context: >-
  The owner wants (2026-10-26) a deployment mode where the AMS and the BI (drmoyassine/ai-native-bi, same stack) run in
  the same Compose project and share the same resources. DEC-017 keeps them separate products with their own storage,
  and the AMS calls the BI over HTTPS only.
decision: >-
  Co-deployment is a deployment mode, not a merge. Shared: one PostgreSQL server, one Garage store, one private network.
  Separate: the AMS keeps its database and bucket, the BI gets its own database, role and bucket (no cross-database
  access, no shared tables); they still talk only through the contract (docs/ams-bi-contract-v0.md) over HTTP. On that
  private network the AMS may call the BI over plain http, but only the one host named by BI_PRIVATE_HOST, which must be
  a single label (a Compose service name such as bi-api) so it can never name a host on the internet. Either product
  still runs alone. The combined Compose file lives in the BI repository and builds the AMS from its own checkout.
rationale: >-
  Saves a database server and a store for small institutions without coupling the products: storage ownership and the
  contract stay as DEC-017 and DEC-032 set them. Plain http is safe only where the address cannot leave the private
  network.
consequences: >-
  New BI_PRIVATE_HOST setting in the AMS (bi-client resolveBiUrl, tested). The BI repository carries
  compose.together.yaml and an init script that creates its database and role on the shared server. The AMS's own
  compose.yaml is unchanged.
